# ADR 0005 (초안 · 적대적 리뷰 대기) — 그래프 저장 포맷 & 마이그레이션 방침

> **이 문서의 목적**: 아직 **결정되지 않은** 설계 포크를 다른 AI에게 **적대적 리뷰**
> 받기 위한 자기완결 문서. 프로젝트를 전혀 모른다는 가정하에 개념부터 설명한다.
> 추천안이 있지만 확정이 아니다 — **§10의 반박 요청 포인트를 공격해 달라.**

---

## 1. 배경 — 이 프로젝트가 무엇인가 (사전지식 0 가정)

### 1.1 Colophon 한 줄 정의
**Colophon**은 마인크래프트(NeoForge 모드) 서버의 게임 로직을 **코드 대신 노드
그래프로 저작**하게 해주는 플랫폼이다. 운영자는 브라우저 **웹 에디터**에서 노드를
끌어다 연결하고 **"Publish"** 버튼을 누른다. 그러면 그래프가 서버로 전송되어 **재시작
없이 즉시 반영**(핫스왑)된다. (언리얼 엔진의 "블루프린트" 비주얼 스크립팅을 마인크래프트
서버 로직에 가져온 것으로 봐도 된다.)

### 1.2 노드 그래프의 개념
- **노드(Node)**: 하나의 연산/동작 단위. 예: `on_player_join`(플레이어 접속 시 발화),
  `get_balance`(잔액 조회), `compare`(두 값 비교), `send_message`(채팅 전송).
- **포트(Port)**: 노드의 입출력 구멍. 두 **범주(category)** 가 있다:
  - **플로우 포트(flow)**: *실행 순서* 를 잇는다. "이 노드가 끝나면 다음은 저 노드." 언리얼
    블루프린트의 흰색 실행 핀에 해당.
  - **데이터 포트(data)**: *값* 을 나른다. 각 데이터 포트는 **타입**(number/string/boolean/
    player 등)을 가진다. 색깔 있는 데이터 핀에 해당.
- **엣지(Edge)**: 두 포트를 잇는 선. 플로우 엣지 / 데이터 엣지.
- 규칙(요약): 플로우 포트와 데이터 포트는 **서로 못 잇는다**. 데이터 엣지는 **같은 타입**
  끼리만. 데이터 입력은 와이어 1개(단일), 데이터 출력은 여러 개로 분기(fan-out) 가능.

### 1.3 노드의 두 종류 (컴파일러로 강제 분리)
- **Exec 노드**: 부작용이 있고 플로우 핀을 가진다(예: 메시지 전송, 변수 저장, 지연).
  값 출력이 있으면 자기 **실행 후** value store에 밀어넣는다(push).
- **Pure 노드**: 부작용 없고 플로우 핀이 없다. 입력을 받아 값을 계산해 돌려준다(예: 산술,
  비교, 텍스트 포맷팅). 필요할 때 당겨서 평가(pull).

### 1.4 "디스크립터" vs "인스턴스"
- **디스크립터(NodeType)**: 노드 *종류* 의 정의. `id`(예: `"send_message"`), 라벨, 카테고리,
  입력 스펙, 출력 포트 목록. 코드(빌트인 또는 애드온)가 등록한다. 그래프 안에는 저장되지
  않고, 그래프는 `nodeType` **문자열로 참조**만 한다.
- **인스턴스(그래프 안의 노드)**: 캔버스에 놓인 한 개. 고유 `id`, 참조하는 `nodeType`,
  그리고 사용자가 채운 **`config`**(예: 보낼 메시지 문자열, 비교 연산자)를 가진다.

### 1.5 publish 파이프라인 (현재 구현)
```
[웹 에디터]  --HTTP POST /api/publish (JSON)-->  [서버]
                                                   │
                                    GraphParser.parse(json)   ← 파싱 + 검증
                                                   │  (검증 실패 시 400 + 에러 목록)
                                                   ├─ 활성 그래프 핫스왑 (메모리)
                                                   └─ 원본 JSON을 디스크에 저장
```
- 검증은 포트/타입/카테고리 인지: 존재하지 않는 포트·타입 불일치·플로우↔데이터 교차 연결·
  데이터 입력 중복 연결을 전부 거부하고 **에러를 모아** 던진다.
- 서버 재시작 시 디스크의 JSON을 다시 `parse` 하여 복원한다.

### 1.6 데이터 포트 "계약(contract)" 이라는 개념 — 왜 신중한가
데이터 포트 모델은 두 가지 이유로 **한번 정하면 바꾸기 어려운 표면**이다:
1. **애드온 SDK 표면**: 서드파티가 이 인터페이스에 대고 노드를 만든다.
2. **저장되는 그래프 포맷**: 운영자가 만든 그래프가 이 포맷으로 디스크에 남는다.

그래서 이 프로젝트는 이 영역을 "구현"이 아니라 **계약**으로 다루고, ADR(결정 기록)로
잠근다. 이미 잠근 계약: 노드 2종 분리, 명목 타입 매칭(서브타이핑 없음), 안정적 포트 ID,
동적 포트 등. **이 문서가 다루는 f = 그중 마지막 조각: "직렬화·버전·마이그레이션".**

## 2. 현재 사실 (코드 근거)

### 2.1 실제로 저장되는 파일의 모습
서버가 디스크에 남긴 실제 `graph.json`(축약, 노드 2개 + 엣지 1개만):
```json
{
  "nodes": [
    {
      "id": "on_player_join_84",
      "type": "colophon",
      "position": { "x": -101.26, "y": 41.31 },
      "data": { "nodeType": "on_player_join", "config": {} }
    },
    {
      "id": "get_balance_85",
      "type": "colophon",
      "position": { "x": 199.32, "y": 38.12 },
      "data": { "nodeType": "get_balance", "config": { "player": "" } }
    }
  ],
  "edges": [
    {
      "id": "xy-edge__on_player_join_84player-get_balance_85player",
      "source": "on_player_join_84",
      "target": "get_balance_85",
      "sourceHandle": "player",
      "targetHandle": "player"
    }
  ]
}
```

이 문서는 **웹 에디터가 쓰는 UI 라이브러리(React Flow)의 문서 포맷 그대로**다. 즉 두
종류의 정보가 **한 파일에 섞여** 있다:

| 런타임 시맨틱 필드 (parse가 **읽음**) | 에디터 UI 상태 필드 (parse가 **무시**) |
|---|---|
| 노드 `id` | 노드 `type: "colophon"` (React Flow 렌더러 종류) |
| 노드 `data.nodeType` | 노드 `position: {x, y}` (캔버스 좌표) |
| 노드 `data.config` | 엣지 `id: "xy-edge__…"` (React Flow 내부 id) |
| 엣지 `source`, `target` | |
| 엣지 `sourceHandle`, `targetHandle` (포트 id) | |

### 2.2 런타임은 지금 "멍청한 저장소(dumb store)" 다
서버는 에디터가 보낸 **JSON 문자열을 한 글자도 안 바꾸고** 그대로 저장하고, 에디터가
다시 요청하면 **그대로 돌려준다**. 자체 직렬화 모델이 없다.
```java
// ColophonRuntime (요지)
public synchronized void publish(String json) {
    GraphParser.Parsed parsed = GraphParser.parse(json); // 검증 + 런타임 그래프 빌드
    this.activeGraph = parsed.graph();                   // 메모리 핫스왑
    this.lastPublishedJson = json;                       // ← 원본 문자열 보관
    save(json);                                          // ← 원본 문자열 그대로 디스크에
}
public String graphJson() { return lastPublishedJson; } // ← /api/graph 가 그대로 반환
```

### 2.3 그래서 UI 레이아웃이 런타임을 "라운드트립" 한다
에디터는 서버에서 되받은 그래프의 `position`으로 **캔버스를 복원**한다:
```js
// 에디터 로드 (요지)
const g = await fetch('/api/graph').then(r => r.json())
loadedNodes = g.nodes.map(n => ({
  position: n.position || { x: 100, y: 100 }, // ← 서버가 준 좌표를 그대로 사용
  data: { nodeType: n.data?.nodeType, config: n.data?.config /* ... */ },
}))
```
**함의**: 서버가 `position`을 버리면, 운영자가 그래프를 다시 열 때 노드 배치가 사라지고
자동 재배치(엉망)된다. 즉 UI 필드는 "쓰레기"가 아니라 **에디터가 서버에 위탁 보관** 중인
상태다.

### 2.4 `parse()`가 읽는 노드 식별 = **`nodeType` 문자열 + `config`** (버전 없음)
파서는 `data.nodeType` 문자열로 디스크립터를 찾고(`NodeRegistry.get`), 못 찾으면 **즉시
에러**. 저장된 노드 어디에도 **버전 숫자가 없다**. config의 "모양"이 몇 버전 기준인지
알 방법이 현재 없다.

## 3. f가 추가하려는 것 (아직 미구현)

ADR 0001이 이미 **설계로 잠근** 계약 f의 내용:
1. **포트 ID = 불변 semantic 문자열** (위치·라벨이 아니라 protobuf 필드 번호처럼 고정). ✅ 이미 지켜짐.
2. **표시 이름 = 번역 키** (ID와 분리).
3. **version = 노드 디스크립터 필드** (`default int version(){ return 1; }`). ID/타입/구조/
   포트 제거가 있을 때만 올린다.
4. **마이그레이션 3층**: ① 관대한 파싱 ② 선언적 리다이렉트(rename) ③ 명시적 마이그레이터.
5. **Deprecation = 노드 단위 soft** (플래그 + 메시지 + 에디터 배지).
6. **진단 `/api/validate`**: 실제 반영 없이 검증만 하는 드라이런 엔드포인트.

**이 문서가 결정하려는 것은 위 목록 자체가 아니라, 그것들이 딛고 설 "저장 포맷/마이그레이션
실행 방침"이다.** (아래 §5)

## 4. 핵심 관찰 — 마이그레이션 3층은 본질적으로 "JSON → JSON" 변환이다

ADR 0001이 정한 3층을, 실제 파이프라인 위 어디에 놓이는지로 다시 보면:

| 층 | 하는 일 | 예시 | 놓이는 지점 |
|---|---|---|---|
| ① 관대한 파싱 | 모르는 필드/구버전 모양을 **터지지 않고** 받아들임 | 사라진 포트 참조 무시 | `parse` **앞** (또는 초반) |
| ② 선언적 리다이렉트 | 옛 `nodeType` 문자열 → 새 문자열 rename | `give_money`→`add_balance` | 타입 해석 **전** |
| ③ 명시적 마이그레이터 | config 값/구조를 옛 버전 → 새 버전으로 변환 | `{amount:"5"}`→`{amount:5}` | 타입 해석 **전** |

세 층 모두 `NodeRegistry.get(nodeType)`으로 **디스크립터를 찾기 전**에, **raw JSON 트리**
위에서 일어난다. 즉:
```
저장된 JSON → [마이그레이션 단계: JSON→JSON] → 최신 모양 JSON → 기존 parse()(검증+빌드)
```
**결론: 마이그레이션은 "빌드된 런타임 그래프"가 아니라 "JSON 문서"를 대상으로 하는 단계이며,
`parse()` 앞에 새로 선다.** 이 사실이 아래 §5의 결정을 강하게 밀어붙인다.

## 5. 결정해야 할 것 — 서로 얽힌 3개 축

"저장 방침"은 사실 **3개의 결합된 하위결정**이다. 하나를 정하면 나머지 선택지가 좁아진다.

1. **저장 포맷**: 디스크에 무엇을 저장하나?
   - (a) 에디터 문서 그대로(UI 필드 포함) — 현행
   - (b) 런타임 전용 정규(canonical) 문서(UI 필드 제거·분리)
2. **version 스탬프 위치**: 저장된 것이 몇 버전인지 어떻게 아나?
   - (a) 안 남김 (parse가 모양으로 추론)
   - (b) 노드별 `data.version` (publish 시 각 노드에 각인)
   - (c) 문서 최상위 `formatVersion` 하나
3. **마이그레이션이 디스크에 언제 반영되나**:
   - (a) 인메모리만 — 로드할 때마다 변환, **디스크 파일은 옛 버전 그대로**
   - (b) 되쓰기(lazy upgrade) — 로드 중 마이그레이션이 일어나면 **변환 결과를 디스크에 저장**

## 6. 세 가지 통합 옵션

위 축들을 현실적인 3개 묶음으로:

### 옵션 A — 패스스루 유지 (현행 + 인메모리 마이그레이션만)
- 포맷=에디터 문서 그대로 / version=안 남김 또는 최소 / 되쓰기=안 함.
- 로드 시 `parse` 앞에서 JSON을 인메모리로 마이그레이트해 빌드만 하고, **디스크는 안 건드림**.

**장점**
- 변경 최소(직렬화기 불필요). UI 필드(position) 보존 공짜.
- 런타임은 계속 dumb store — 개념 단순.

**단점**
- 디스크 파일이 **영원히 옛 버전**으로 남는다. 오래 안 열린 그래프를 위해 **옛 마이그레이션
  코드를 영구히 못 버린다** (마이그레이션 은퇴 불가 → 시간이 갈수록 누적).
- 매 로드마다 전체 마이그레이션 수행.
- 파일에 **버전 표식이 없어** 파일 하나만 보고 나이를 알 수 없다(진단·지원 곤란).

### 옵션 B — 쓰기 시 정규화(canonical)
- 포맷=런타임 정규 문서 / version=문서 or 노드 / 되쓰기=항상(정규화가 곧 쓰기).
- publish 시 `parse → migrate →` **런타임 정규 JSON으로 재직렬화**하여 저장.

**장점**
- 디스크가 **항상 최신 버전**. 마이그레이션을 자연히 은퇴시킬 수 있다.
- 라운드트립 테스트가 명확한 정규형을 대상으로 assert.

**단점**
- **UI 상태(position/레이아웃) 소실 위험** — 별도 채널로 보존하지 않으면 에디터 재로드가
  자동배치로 퇴행(§2.3). 보존하려면 결국 UI 필드를 어딘가 저장해야 함 → 정규화의 순수함이
  깨짐.
- **런타임→JSON 직렬화기를 새로 작성**해야 한다(현재 없음, §2.2). 유지보수 표면 증가.
- 이제 포맷이 사실상 둘(에디터 문서 ↔ 런타임 정규)이라 **동기화 부담**.

### 옵션 C — 하이브리드 (추천 후보)
- 포맷=**에디터 문서를 저장 포맷으로 유지**(UI 필드 패스스루) / version=**노드별 `data.version`
  각인** / 되쓰기=**마이그레이션 발생 시 lazy upgrade**.
- 마이그레이터는 **런타임 시맨틱 필드만** 건드린다(`nodeType` 리다이렉트, `config`/포트 키
  rename/변환). **UI 필드(position 등)는 무손실로 통과**시킨다.
- publish 시 각 노드에 현재 디스크립터의 version을 찍어 저장. 로드 시 저장된 version <
  현재 version인 노드만 골라 마이그레이트하고, 변환이 있었으면 문서를 되쓴다.

**장점**
- UI 상태 보존(패스스루) **그리고** 디스크 점진 최신화(마이그레이션 은퇴 가능) — A와 B의
  좋은 쪽을 동시에.
- 별도 정규 직렬화기 불필요: **읽은 JSON 트리를 그대로(시맨틱 부분만 갱신) 되쓴다.**
- 파일에 버전 표식 존재 → 진단·`/api/validate` 리포트가 구체적.
- §4의 "마이그레이션 = JSON→JSON, parse 앞단" 구조와 정확히 일치.

**단점 / 비용**
- 마이그레이터가 **빌드된 그래프가 아니라 raw JSON 트리를 편집**해야 한다. (반론: 이게 3층
  계약상 원래 맞는 계층이라 오히려 자연스럽다.)
- 되쓰기 = 로드가 **디스크 쓰기 부작용**을 가진다(멱등이어야 하고, 실패 시 정책 필요).
- 시맨틱/UI 필드 경계를 마이그레이터가 존중하도록 **규율**이 필요(실수로 UI 필드를 건드리면
  레이아웃 깨짐).

### 요약 비교표
| 축 | A 패스스루 | B 정규화 | C 하이브리드 |
|---|---|---|---|
| UI(position) 보존 | ✅ 공짜 | ⚠️ 별도 보존 필요 | ✅ 패스스루 |
| 디스크 항상 최신 | ❌ | ✅ | ✅ (lazy) |
| 마이그레이션 은퇴 | ❌ 불가 | ✅ | ✅ |
| 새 직렬화기 필요 | ❌ | ✅ 필요 | ❌ |
| 파일 버전 표식 | ❌ | ✅ | ✅ |
| 로드의 쓰기 부작용 | 없음 | 없음(publish서 씀) | ⚠️ 있음(되쓰기) |
| 구현 크기 | 최소 | 큼 | 중간 |

## 7. version 스탬프 위치 하위결정

- **(b) 노드별 `data.version`** — publish 시 각 노드에 그 디스크립터의 version을 각인.
  - ADR의 "version = 디스크립터 필드"와 일치. ③ 값 마이그레이터가 **노드마다** 출발 버전을
    알 수 있다(애드온별로 버전이 제각각 오르므로 이게 자연스럽다).
- (a) 안 남김 — 마이그레이터가 config "모양"으로 버전을 역추론해야 함 → 취약·모호.
- (c) 문서 `formatVersion`만 — 단순하지만 노드마다 다른 버전(애드온 개별 업그레이드)을
  표현 못 함. 그래프 **구조 자체**(엣지 포맷 등)가 바뀌는 드문 경우엔 유용 → (b)와 **병행**
  가능.

**추천: (b) 노드별 `data.version`을 기본**으로, 그래프 구조 레벨 변경에 대비해 최상위
`formatVersion` **한 칸을 열어두기**(당장 안 써도 예약).

## 8. 추천안 (확정 아님 — 리뷰 대상)

> **옵션 C + 노드별 `data.version`(+ 예약된 문서 `formatVersion`).**
> 마이그레이션은 `parse()` 앞에 서는 **JSON→JSON 단계**로 구현하고, UI 필드는 무손실
> 패스스루하며, 마이그레이션이 일어난 로드는 결과를 디스크에 되쓴다(lazy upgrade).

**근거 요약**
1. UI 상태 보존이 실제 요구사항이다(§2.3) → B의 순수 정규화는 대가가 크다.
2. 마이그레이션을 언젠가 **은퇴**시키려면 디스크가 최신화돼야 한다 → A는 이 축에서 진다.
3. 마이그레이션은 어차피 JSON→JSON, parse 앞단이다(§4) → "읽은 모양 되쓰기"가 자연스럽고
   **새 직렬화기가 필요 없다.**
4. 노드별 version이 애드온 생태계(제각각 버전 상승)와 ③ 값 마이그레이터에 맞다.

## 9. 라운드트립 테스트가 각 옵션에서 assert하는 것 (f는 직렬화 계약 테스트 1층급 우선)

이 프로젝트는 "저장 표면"은 잠긴 계약이자 버그 시 **저장 데이터 손상**이라 치명적이므로,
f 구현과 **함께** 계약 테스트를 붙이기로 이미 정했다. 옵션에 따라 테스트가 무엇을 보장하는지가 달라진다:

- **A**: `migrate(old) == 런타임 그래프` 동치성만. 디스크 불변 → "파일이 최신"이라는 보장은 애초에 없음.
- **B**: `serialize(parse(x))`가 정규형이라는 **고정점(fixed-point)**: `normalize(normalize(x)) == normalize(x)`.
- **C**: (1) **멱등성** `migrate(migrate(x)) == migrate(x)`, (2) **UI 보존** `migrate(x).position == x.position`,
  (3) **버전 단조성** 출력 노드 version == 현재 디스크립터 version, (4) 구체 마이그레이션 케이스별 값 변환.

## 10. 가정과 반박 요청 포인트 (← 적대적 리뷰는 여기를 공격해 달라)

1. **"UI 상태 보존은 진짜 요구사항인가?"** — position을 서버가 보관하는 현재 설계가 옳은가?
   에디터가 로컬(localStorage)에 레이아웃을 두고 서버엔 시맨틱만 보내면 B의 단점이
   사라지고 관심사가 깔끔히 분리된다. **이 대안이 C보다 낫지 않은가?**
2. **"로드가 디스크에 되쓰는 부작용(C)이 위험하지 않은가?"** — 읽기 경로의 쓰기는
   동시성·실패·권한 문제를 부른다. 되쓰기를 publish 시로만 미루면(=사용자가 다음에 저장할
   때 최신화) 마이그레이션 은퇴가 늦어질 뿐 안전해진다. **lazy upgrade의 값어치가 그 리스크를
   정당화하나?**
3. **"마이그레이션을 정말 은퇴시킬 일이 있나?"** — 취미 규모 프로젝트에서 옛 마이그레이션
   코드 누적(A의 단점)이 실제로 문제가 될 만큼 커지나? 그렇지 않다면 **가장 단순한 A가
   승자**일 수 있다. (YAGNI 반론.)
4. **"노드별 version 각인이 저장 포맷을 오염시키지 않나?"** — 사용자가 손으로 그래프 JSON을
   읽을 때 version 잡음이 늘고, 에디터가 매번 찍어야 하며, 서버가 신뢰할 수 있는지(위조된
   version) 문제가 있다. **차라리 서버가 로드 시 디스크립터로 추론하는 게 낫지 않나?**
5. **"raw JSON 트리 편집(C/③)이 타입 안전성을 버리는 것 아닌가?"** — 빌드된 그래프 대신
   문자열 키 JSON을 만지면 오타·구조 실수가 컴파일러에 안 잡힌다. 마이그레이터를 위한
   중간 표현(경량 DTO)을 두는 게 나은가, 과설계인가?
6. **"관대한 파싱(①)과 엄격한 검증이 충돌하지 않나?"** — 지금 parse는 모르는 타입을 **즉시
   거부**한다(안전). ①이 이를 완화하면, 조용히 노드를 드롭해 **의도와 다른 그래프가 publish**
   될 위험이 생긴다. 관대함의 경계는 어디여야 하나? (드롭 vs 거부 vs 격리)
7. **환경 제약 하나**: 이 저장소는 에이전트 환경에서 **Java 컴파일이 금지**(NeoForge 빌드가
   무겁고 캐시가 꼬임)라, 검증은 CI(push 후) 또는 사용자 IntelliJ로만 한다. **즉 "짧은
   반복 컴파일 루프"가 불가능**하다 — 이 제약이 "가장 단순한 옵션 선호"로 저울을 기울여야
   하는가?
